# BlockStock 玩家公司经营财务、月报与分红设计

日期：2026-08-28  
状态：已完成设计评审，待实现

## 1. 结论与边界

现有系统已经具备统一的 15 天分红结算：上市玩家公司以 `company_cash_accounts.retained_earnings_minor` 作为利润，以可用公司现金作为付款来源；亏损或利润为零时不分红；分红进入股东证券账户；`dividend_runs`、公告、审计和托管账本保证重试幂等。

本阶段不重写该结算器。缺口是没有受信任的经营流水把“绑定资产的实际收入/成本”归入公司账户，也没有给玩家看的固定周期财务报告。实现后，玩家公司与系统蓝筹共用现有 15 天分红规则，但玩家公司的利润只来自已验证、可去重的经营事件，绝不从个人钱包或注册资本虚构产生。

本设计只覆盖：

1. 已绑定资产的经营收入/成本入账；
2. 每月财报快照与公司中心查看；
3. 与已有 15 天分红链路的正确衔接与完整测试。

增发投票、回购/创始人套现公告、退市与补偿基金为后续三个独立阶段，不能借本阶段的公司现金接口绕过其治理流程。

## 2. 事实基线

已验证的现有行为：

- `SqlBluechipRepository.settleDueDividendRuns` 遍历所有上市公司；玩家公司的利润取留存收益，分红比例取公司创建时选择的 `dividend_basis_points`。
- 结算周期从上市日起每 15 天一次；`dividend_runs` 的唯一 `(company_id, dividend_at)` 抢占记录防止重复分红。
- 分红按全部可用和冻结持仓比例记入 `securities_cash_accounts`；扣减公司现金、留存收益与公司托管账本；利润非正或可付资金为零时发布 `NO_DIVIDEND` 而不付款。
- 现有原生资产明确显示“不会自动产生收益”；当前适配器协议只有归属验证，不读取商店/产线/任务等经营事件。因此“绑定”不等于“已有收入”。

## 3. 目标体验

公司创建人绑定可产生收入的资产后，兼容适配器会把该资产实际发生的、可验证的收款或成本事件自动归属到公司。玩家在公司中心的“财务与分红”页能清楚看到：本月收入、成本、净利润、累计留存收益、公司可用资金、下一次分红时间和上一次分红结果。

每个自然月结束后，系统为上市公司生成一次不可变月报并发布简洁公告。月报不是分红开关：分红仍按 15 天周期、只以当时正的留存收益和可用现金为上限。出现亏损则该次分红显示“本期亏损/无可分配利润”，不会扣款。

## 4. 数据模型

新增 V015 迁移，包含：

### 4.1 `company_operating_events`

字段：`id`、`company_id`、`binding_id`、`adapter_id`、`external_event_key`、`kind` (`INCOME`/`EXPENSE`)、`amount_minor`（严格大于零）、`occurred_at`、`recorded_at`、`metadata_json`。

约束：

- `UNIQUE(adapter_id, external_event_key)`：同一外部流水永远只记一次；
- `binding_id` 必须是当时有效绑定且属于同一公司；
- 仅接受适配器明确给出的正数绝对金额，方向由 `kind` 决定；
- 元数据只保存无敏感的来源标识/显示摘要，不保存经济插件账户凭据。

### 4.2 `company_monthly_reports`

字段：`company_id`、`period_start`、`period_end`、`income_minor`、`expense_minor`、`net_profit_minor`、`retained_earnings_minor`、`cash_minor`、`generated_at`。

主键 `(company_id, period_start)`。报告为不可变快照，重复调度只读取已生成报告；报告公告 ID 由公司和周期确定，防止重复公告。

## 5. 领域与应用接口

新增小型端口 `CompanyOperatingEventSource`，由可选资产适配器实现：

```java
String adapterId();
List<VerifiedOperatingEvent> readSince(AssetBinding binding, Instant afterExclusive, Instant throughInclusive);
```

`VerifiedOperatingEvent` 必须包含稳定外部事件键、发生时间、收入/成本方向、金额和展示摘要。适配器对来源插件 API 的调用仍在 Bukkit 主线程；数据库落账在异步事务中完成。

新增 `CompanyOperationsService`：

1. 读取活跃绑定与相应事件源；没有事件源的绑定跳过，不报错；
2. 对每笔事件先验证适配器 ID、绑定归属、发生时间和金额；
3. 以数据库唯一约束为最终幂等保障插入事件；
4. 收入：增加 `cash_minor` 和 `retained_earnings_minor`，追加正的 `COMPANY_TREASURY` 托管账本；
5. 成本：仅当可用现金足够时减少 `cash_minor` 和 `retained_earnings_minor`（不允许留存收益为负）；不足时事件保留为拒绝审计，不记账；
6. 对所有成功或拒绝事件写结构化审计记录，不直接修改玩家个人/证券账户。

为保持“亏损不分红”且支持真实成本，留存收益模型须允许负值，或另行存储累计亏损。本阶段采用新增 `accumulated_loss_minor`：成本先冲减留存收益，超出部分累积为亏损；后续收入先抵消累计亏损，剩余才成为留存收益。这样现有分红器仍只读非负的 `retained_earnings_minor`，无需更改付款语义。

因此 V015 还给 `company_cash_accounts` 新增 `accumulated_loss_minor INTEGER NOT NULL DEFAULT 0 CHECK (accumulated_loss_minor >= 0)`。财报净利润可以为负，但可分配留存收益永远不会为负。

新增 `CompanyFinancialReportService`：每小时检查已经结束、尚未生成的自然月；为所有上市玩家公司按经营事件聚合收入和成本、读取结账后余额，插入月报、`MONTHLY_REPORT_PUBLISHED` 审计以及 `MONTHLY_REPORT:` 公司公告。它不更改收入与分红余额。

## 6. 适配策略与安全边界

本阶段先落地事件标准、数据库和调度器；每种外部插件的事件采集另作为对应适配器实现和兼容性测试。原因是商店、领地、产线、任务插件的“收入”定义不同：只凭资产所有权不能安全推断经济流水。

- QuickShop：只有在其可用 API 提供已完成交易的唯一交易 ID、金额、店铺标识时才实现收入源；不扫描箱子物品变动推测收入。
- 领地插件（Lands / GriefPrevention / Residence）：只有租金、税收或明确经济结算事件才纳入；领地本身不会凭空产生利润。
- 产线/任务插件：仅接入能提供稳定任务/生产结算 ID 和金额的插件；否则只保留“已绑定资产”展示。
- 原生资产：持续显示“未接入收益源”，不制造收入；未来可以由 BlockStock 自己的原生产线/委托模块产生同样的验证事件。

外部事件可延迟到达；读取窗口按水位线回补，数据库唯一键去重。适配器故障仅记录诊断并跳过本轮，不能阻塞市场、分红或其他公司。

## 7. GUI 与文案

在“公司中心”新增 `财务与分红` 按钮：

- 第一屏：公司可用资金、留存收益、累计亏损、本月收入/成本/净利润、距下一次分红的时间；
- 第二屏：最近 6 份月报，点击查看明细；
- 第三屏：最近分红结果（日期、盈利/亏损、派发金额、持有人数）。

文案必须使用中文，并明确区分“公司账户”“证券账户”“个人钱包”。没有收益源的绑定使用黄色提示“已绑定，尚未接入自动收益来源”，而不是误导为已产生利润。

## 8. 调度、并发与失败恢复

- 经营事件采集：默认每 5 分钟，可配置；
- 月报：默认每小时检查一次，按服务器时区自然月；
- 分红：保留当前定时器和 15 天周期；
- 所有资金变化、事件插入、审计和托管账本在同一数据库事务；
- 事件唯一键、月报主键、分红运行记录三层幂等，服务重启/重复点击/重复回调均不会重复入账或派息；
- 任何外部经济插件调用都只读其完成事件；BlockStock 不会从其 API 主动扣划公司或玩家钱包来“补齐”收入。

## 9. 测试与验收

先写失败测试，再实现。最低覆盖：

1. 收入事件首次入账，重复事件不重复增加公司现金、留存收益、账本或审计；
2. 成本先消耗留存收益，超额部分进入累计亏损；后续收入先抵亏；
3. 非活跃/非本公司绑定、金额非法、事件时间非法全部拒绝；
4. 调度器中一个适配器失败不影响另一个适配器及下一轮；
5. 已存在的玩家公司 15 天盈利、亏损、重启重试和托管对账测试继续通过；
6. 月报聚合金额正确、同一周期只生成一次公告和审计；
7. GUI 显示三类账户和无收益源提示，返回路径可用；
8. 在隔离 Paper 环境以创建人/股东两个真实机器人执行：绑定→产生可验证事件→查看报表→推进结算→核对证券账户与数据库账本。

验收时更新需求追踪：GV-01 从“未实现”改为“已实现（经营事件源仅对已完成兼容适配器生效）”；不把未完成的 QuickShop/领地/产线/任务采集器错误标为已兼容。
