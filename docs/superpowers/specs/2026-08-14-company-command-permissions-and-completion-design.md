# 公司命令权限与 Tab 补全设计

## 目标

将公司命令明确划分为玩家与管理员两类，并为有权限的发送者提供安全、无需数据库查询的 Tab 自动补全。

## 权限模型

| 角色 | 权限节点 | 默认值 | 能力 |
| --- | --- | --- | --- |
| 玩家 | `blockeco.company.create` | `true` | 创建公司 |
| 玩家 | `blockeco.company.info` | `true` | 查询公司 |
| 管理员 | `blockeco.admin.recovery` | `op` | 查看恢复记录 |
| 权限组 | `blockeco.player` | `true` | 聚合两项玩家权限 |
| 权限组 | `blockeco.admin` | `op` | 聚合管理员恢复权限 |

命令执行层继续逐项检查具体节点，权限组只用于权限插件授予和文档说明。控制台不能创建公司；查询和恢复仍遵循对应权限。

## Tab 补全

采用 Paper 1.21.4 官方 `TabCompleter` + `PluginCommand.setTabCompleter` 接口。该回调只返回当前最后一个参数的候选值，因此完成器只使用内存常量，不在主线程读取 SQLite。

- 第一个参数：仅返回发送者拥有权限的 `create`、`info`、`recovery`。
- `create`：公司名称位置不猜测；已有至少一个名称参数后，仅建议 `30`、`50`、`70`，按当前前缀过滤。
- `recovery`：仅具备 `blockeco.admin.recovery` 的发送者可获得 `list`。
- `info`：不读取公司名列表，返回空建议，避免同步 SQL 和泄露公司名称。
- 未授权发送者不获得受限子命令建议；手工输入仍由现有命令处理器给出中文无权限提示。

## 生命周期与验证

在异步 SQLite 初始化之前即安装同一个补全器，保证启动窗口不会回退到 Paper 的默认玩家名称补全。准备就绪后只替换执行器，不替换补全器。

测试使用 MockBukkit 风格的 `CommandSender` mock 与直接调用完成器：验证各角色根命令隔离、恢复隔离、股息档位/前缀、多词公司名、控制台以及没有数据库访问。验证 `plugin.yml` 权限描述/children 与运行时节点一致，并在本地 Paper 重启后由 `Aoozzz` 实测 Tab 候选与权限拒绝。

## 非目标

- 不增加中文命令别名。
- 不通过 Tab 补全查询或暴露数据库中已存在公司。
- 不增加权限插件依赖。
- 不修改交易、分红或恢复业务规则。
